> 本文整合两部分内容并给出统一优先级与执行顺序：

## 0. 背景与证据（本次生产检视快照）

以下为 2026-09-03/04 对生产服务器（`whop-wechat-bridge`）只读诊断得到的真实数据，作为方案依据：

| 观察项 | 现状证据 |
|---|---|
| 事件循环曾被占死 | 主线程曾持续 99.9% CPU（30 分钟里 25 分钟 CPU），8085 全超时（已修复 ISR 重复分发） |
| 本地 14B 依赖 SSH 隧道 | `news_map` 失败 **1455 次 `ECONNREFUSED 127.0.0.1:8080`**（隧道断即全失败） |
| Gemini 配额/密钥 | `news_reduce` 失败 **694 次 429 配额耗尽 + 351 次 401 密钥失效**（失败率 ~93%） |
| task_queue 被污染 | 表 **28,051 行，其中 22,285 行是 `gemini_api_cloud` 可视化记录（79%）** |
| 附件未回填 | `messages.attachments` 全为 `[]`/`null`；磁盘图片 139 张 vs manifest 126 条 |
| 队列无消费者 | `pipeline_tasks`：`l2a_cut` 295 pending、`timeline` 53 pending 长期无人消费 |
| 水位滞后 | `wm_media` 落后主水位 5.3h；L2a 水位停在 08-31（滞后 ~3.5 天） |
| 离线资产滞后 | Persona 画像最新 08-26（滞后 8.4 天） |
| 资源与日志 | DB 867MB；pm2 日志曾涨到 945MB（已加轮转） |

## 1. 不合理之处与改法（来自整体检视）

| # | 问题 | 影响 | 改法 |
|---|---|---|---|
| I1 | 本地 14B 靠 `ssh -R` 隧道映射到 `127.0.0.1:8080`（服务器 958MB 跑不动模型） | 隧道一断，所有 bulk AI（news_map/persona_map）`ECONNREFUSED` 全失败 | 隧道健康探活 + 断线自动降级（暂缓入队/切云端稀疏兜底）+ 告警；长期评估常驻推理机或托管推理 |
| I2 | Gemini 免费配额远不够、密钥池含失效 key | news_reduce 大面积 429/401 | 清理失效 key、修复轮换、reduce 也优先本地、失败退避重排而非直接 fail、配额水位告警 |
| I3 | `rate-limiter` 用 `task_queue` 表存 API 可视化卡片 | 任务表膨胀（79% 脏数据）+ 被 worker 误当任务（"Unsupported task type"） | 改用独立表/内存环形缓冲；清理历史 22k 脏行；worker 只认真实任务类型 |
| I4 | `normalizedMessages` 丢弃 attachments + `saveMessages` 为 `INSERT OR IGNORE` | `messages.attachments` 结构化附件全空；DPC `media` 队列空转 | 归一化时保留 attachments 并在下载后回填；校正媒体三层一致性 |
| I5 | `pipeline_tasks` 六队列仅 `media` 有在线消费者 | `l2a_cut`/`timeline` 入队即积压，队列语义名存实亡 | 落实消费者：在线 worker 或定时（cron）跑离线脚本并推进水位 |
| I6 | 离线资产（persona/L2a）靠轮询内时点判断触发 | 漏触发即长期滞后（persona 8 天、L2a 3.5 天） | 改为可靠定时调度（pm2 cron / 系统 cron），带成功/滞后监测 |

## 2. 监测机制（中断响应式）

### 2.1 框架
```
子系统探针(HealthProbe: check/周期/阈值/级别)
  → 统一调度器(Supervisor) → 状态机(ok/warn/critical, 边沿触发+冷却抑制)
  → 告警路由(企业微信分级) / 自愈钩子(可选) / health_events(历史) / /api/health + 看板
```
原则：边沿触发（进入/恢复各告警一次）、冷却去抖、告警含「子系统+现象+证据数值+建议动作」。

### 2.2 两个基石（必须最先有）
- **M0-A 外部看门狗**：`pm2` 独立轻量进程（或系统 cron）定期 `curl /health`，超时/非 200 即告警。解决"主进程卡死时自己发不出告警"的悖论。
- **M0-B 事件循环延迟探针**：`perf_hooks.monitorEventLoopDelay()`，`>1s` warn / `>5s` critical。卡顿的最直接信号。

### 2.3 分子系统监测清单
| 组 | 子系统 | 关键监测项 | 异常判据 |
|---|---|---|---|
| A | 运行时 | 事件循环延迟、内存、pm2 重启、未捕获异常、磁盘 | lag>阈值 / RSS 近上限 / 重启突增 / 磁盘>85% |
| B | 数据抓取 | 抓取心跳、单轮耗时、同步锁卡死、Whop 失败、抓取量 | 交易时段水位停滞 N 分钟 / 单轮超时 / 连续 fetch 失败 |
| C | 处理与队列 | 队列积压、无消费者、水位滞后、running 卡死、失败率 | pending 超阈值 / done 长期不增 / wm 落后 / 失败率突增 |
| D | AI 供给 | 本地 14B 隧道探活、Gemini 配额、401/429 率、模型卸载 | 8080 探活失败 / 配额近上限 / 失败率高 |
| E | 资产新鲜度 | Persona/L2a/News/Timeline 距上次更新 | 超预期周期未更新 |
| F | 推送/交易 | 微信推送成功率、待推送积压、跟单失败率 | webhook 不可达 / is_pushed·is_traded 积压 |
| G | 前端渲染 | API p95 延迟、前端 RUM（首屏/fetch/长任务/掉帧）、前端错误 | 延迟超阈值 / 长任务>50ms / onerror |
| H | 数据一致性 | 附件回填、manifest·磁盘·DB 三方一致、打标覆盖、水位单调 | 有图但 attachments 空 / 数量偏差 / 覆盖率低 / 水位倒退 |

> 说明：把「加固项 I*」与「监测项 M*」合并排序。复杂度用技术范围描述（不用日历时间）。

### 阶段 P0 — 止血与"出事能知道"（先做）

## 4. 需要你确认的决策点（Open Questions）

1. **本地 14B 供给**：仅做"隧道健康探活+断线降级+告警"，还是同时规划常驻推理机/托管推理？（影响 I1 的深度）
2. **Gemini 策略**：是否升级为付费配额？还是坚持"本地优先、云端仅稀疏兜底"，配额耗尽即降级不告警升级？
3. **队列消费者形态**：`l2a_cut`/`timeline` 用「在线常驻 worker」还是「系统 cron 跑离线脚本」？（后者更贴合当前在线/离线硬隔离约束）
4. **告警渠道**：企业微信是否足够？是否需要@特定人、分群、或加邮件/其他渠道？告警冷却窗口设多长（如 critical 10min、warn 聚合日报）？
5. **自愈动作授权**：哪些允许自动执行（如 running 卡死回收、磁盘高触发清理、AI 断线自动暂缓入队），哪些只告警不自动处理？
6. **监测数据存储**：`health_events` 用主库新表，还是独立 sqlite 文件（避免与业务库竞争写锁）？
7. **前端 RUM**：是否接受在 `public/app.js` 注入轻量埋点并上报到后端？
8. **看门狗形态**：pm2 独立进程即可，还是需要真正的"进程外/机器外"探测（更强，但需另一台机器/外部服务）？

## 5. 建议

- 先合入 **P0**（止血 + 让系统出事能第一时间报出来），用真实故障注入验证告警链路；
- 再按 P1 → P2 推进，每合并一项同时更新"已做/待做"清单；
- 每一阶段都保持"旁路增量、不侵入主流程"的原则，降低对生产的风险。
